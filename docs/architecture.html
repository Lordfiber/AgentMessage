多 TRAE 任务分发系统 · 整体设计

局域网内 3 台 Windows + TRAE：主 Agent（Orchestrator）编排研发状态机，经 Kafka 分发阶段任务，Worker 上的角色 Agent 定时触发执行，知识库中间层沉淀与召回经验。

TypeScript / Node.js Kafka (KRaft, 服务器部署) trae-cli 非交互触发 Windows 计划任务 知识库中间层（黑盒） 两套 Agent 体系（Orchestrator + 5 角色） markitdown 输入清洗（仅 Orchestrator） 端到端链路追踪 · trace_id 贯穿 + 每步容错 Agent 完成 Hook（黑盒后端） Agent 统一管理层（中间件管道）

组件说明

TRAE-A · 主 Agent（Orchestrator）

orchestrator

唯一实例，跑研发状态机（PM→Dev→Review→QA→Deploy）。每阶段把工作封装为任务消息（type=角色）→ produceTask 投递 Kafka；消费 results 推进状态机；3 道人工门禁；Review 不通过回退 Dev（≤3轮）。收口读 runtime/results 聚合 + 写知识库。

TRAE-B/C · 角色 Agent（Worker）

worker / role agent

承载 5 角色之一（pm/dev/review/qa/deploy）。计划任务每 N 分钟唤醒：consumeTasks 拉任务 → 知识库 query → trae-cli run --file 执行角色职责 → 写结果 → 知识库 ingest → publishResults。

Kafka 服务器

message bus

独立服务器部署（Linux KRaft 最稳，也可 Docker/WSL2/Windows）。三主题：agent-tasks（按 worker_id 分区，保序）、agent-results、agent-control（stop/pause/resume）。持久化、可回放、worker 离线不丢任务。

知识库中间层（黑盒）

knowledge layer

不关心内部实现（向量库/全文/图谱皆可）。对外仅两个方向：写入总结的知识、查询获取本次需要的知识。供编排者与 Worker 在执行前后调用，沉淀经验、召回上下文。

触发器与计划任务

scheduler

workerPoll.ts 文件锁防重入 + 检测 control stop 信号；triggerTrae.ts 可插拔（trae-cli 首选，IDE-UI 兜底）；registerTasks.ts 用 PowerShell 注册 Windows 计划任务。

markitdown · 输入清洗层

orchestrator-only

只在 Orchestrator/TRAE-A 启动时调用（仅它接收杂格式：doc/docx/pdf/txt/企业微信消息/手动输入）。命令：markitdown nio.pdf > nio.md。统一清洗为 Markdown 再喂给 LLM；markitdown 不可用/失败时原样回退，不中断流程。代码入口：src/orchestrator/normalizeInput.ts。

Broker 桥接层

zero-token I/O

所有 Kafka 连接/轮询/回传都在 TS 脚本里，agent 不参与。produceTask / consumeTasks / publishResults / consumeResults + 契约校验 + 死信目录。

Agent 统一管理层（中间件管道）

cross-cutting concerns

所有 agent 生命周期事件经 emitAgentEvent(ctx) 管道分发。横切关注点（hook/评审/总结/审计/token 统计）注册为中间件，加新关注点 = useAgentMiddleware 一行，零改动 agent 代码。入口 src/agent/。解决"每个 agent 后面重复加 hook/评审/总结"的冗余。

Agent 完成 Hook（中间件①）

audit / monitor / BI

统一管理层的第①个中间件：把 agent 完成详情 POST 到 AGENT_HOOK_URL 黑盒后端。未配置 → no-op；失败 → 落 runtime/hooks/_failed/，不中断主流程。底层传输 src/broker/hookReport.ts。

Agent 统一管理层（中间件管道 · 横切关注点集中化）

问题：每加一个横切关注点（hook、评审、总结、审计、token 统计...）都要在每个 agent 后面重复一遍——冗余且易漏。

方案：所有 agent 的生命周期事件都经 emitAgentEvent(ctx) 统一管道分发；每个关注点注册为一个中间件，管道依次执行。加新关注点 = useAgentMiddleware 一行，零改动任何 agent 代码。

数据流

① 任务分发流（Kafka 主链路）

0
markitdown 输入清洗（仅 Orchestrator）：杂格式原始输入 → npx tsx src/orchestrator/normalizeInput.ts <原始文件>（或 --text）→ 产出 runtime/input-clean/xxx.md，再把这份清洗后的 .md 喂给 LLM。失败/不可用自动原样回退，不中断。
1
Orchestrator 分发阶段任务：基于清洗后的 .md 内容，按状态机当前阶段，把工作封装为任务消息 JSON（type=角色，含 directive + expected_output）→ npx tsx src/broker/produceTask.ts <task.json> 投递到 agent-tasks，key=worker_id。PM 阶段由 PM Agent 拆任务，Dev 阶段并行分发多个 dev 任务。
2
Worker 拉取：计划任务触发 workerPoll → consumeTasksForWorker 消费分给自己的消息 → 渲染 inbox/<task_id>.md + .json，按 task_id 去重。inbox 为空则直接退出（零开销）。
3
Worker 执行：triggerTrae 调 trae-cli run --file <task_id>.md --output <result_file>，按 timeout_sec/max_steps 控上限，退出码映射 status。
4
结果回传：publishPendingResults 把 outbox 的结果生产到 agent-results → 编排者 consumeResults 落 runtime/results/。
5
收口：编排者读 runtime/results 聚合；失败可修正后重新 produce。

② 知识库交互流（黑盒，两方向）

Q
查询获取（执行前）：Worker 拿到任务后、执行前，向知识库发查询请求（任务目标 + 关键词），获取本次内容需要的知识（历史经验、相关模式、上下文），作为 directive 之外的补充上下文注入 .md。编排者拆任务时也可查询以辅助拆解。
W
写入总结（执行后）：Worker 执行完成后、回传结果前，向知识库发写入请求，把本次的总结知识（做了什么、踩了什么坑、可复用的模式）沉淀进去。编排者收口后也可写入整体总结。
知识库中间层是黑盒：系统只约定"查询 / 写入"两个交互方向与请求/响应字段，内部存储、检索算法、向量化等一概不关心，可按需替换实现。

端到端链路追踪（trace_id 贯穿 + 每步容错）

一条需求从输入主 Agent 到被分发到的角色 Agent 处理，全程用链路唯一 ID（trace_id）串起来；每一步都通过 Agent 完成 Hook 把事件上报到黑盒后端（不再本地保存状态文件），任何一步出错都有对应的容错动作。这条链路是本系统的主干，比"数据流"更具体地展示了一个请求的完整生命周期与容错路径。

① 三级 ID 体系

ID谁生成粒度用途
trace_idOrchestrator（需求输入时）一条需求一条，贯穿 PM→Dev→Review→QA→Deploy 全程链路唯一标识，串联所有阶段/子任务/事件；这是用户给的"链路唯一 ID"
parent_task_idOrchestrator（每阶段切换时）一个阶段一个该阶段所有并行子任务的共同父 ID，便于阶段级聚合
task_idOrchestrator（分发每个子任务时）一个子任务一个Kafka 消息 key 之一、worker 去重、结果回传对账

关系：trace_id 1 → N parent_task_id（每阶段 1 个）→ N task_id（阶段内并行子任务）。所有 Kafka 消息（task / result / control）都带 trace_id，worker 也会把 trace_id 写进产出文件头。

③ 一条链路的完整时间轴（从 nio.pdf 到 dev 处理完成）

标记说明：🔤 消耗 Token = 该步骤调 LLM 消耗 token；— 无 Token = 纯脚本/人工/黑盒 I/O，不消耗系统 token。

0
需求输入：用户把 nio.pdf 交给 Orchestrator/TRAE-A。生成 trace_id=tr-20260803-0001，hook 上报 trace_created。— 无 Token
0.1
markitdown 清洗：normalizeInput.ts nio.pdf → runtime/input-clean/nio.pdf.md，hook 上报 normalized（带 converted 标志）。— 无 Token（格式转换）
1
进入 PM 阶段：Orchestrator 把清洗后的 .md 喂给 PM 角色，生成 parent_task_id=p-...-0001 + task_id=t-...-0001，produceTask 投 agent-tasks，hook 上报 produced。🔤 消耗 Token（主 Agent 拆任务）
2
Worker 拉取：worker-B 计划任务触发 workerPoll，consumeTasksForWorker 拉到 t-...-0001，渲染 inbox .md，hook 上报 consumed。— 无 Token（Kafka I/O）
3
Worker 执行前：向知识库 query 本次需要的知识，注入任务 .md。hook 上报 running。— 系统侧无 Token（黑盒内部自理）
4
Worker 执行：trae-cli run --file t-...-0001.md --output ... 跑 PM 角色职责，产出 pm.md（PRD+任务卡+DAG）。🔤 消耗 Token（主要，角色 Agent 调 LLM）
5
Worker 执行后：把本次总结 ingest 进知识库；写 outbox 结果 JSON（含 trace_id）。— 系统侧无 Token
6
结果回传 + 双 hook：worker hook 上报 agent_complete（角色 agent 做完了，携带本次 token_usage）→ publishPendingResults 投 agent-results → Orchestrator consumeResults → hook 上报 stage_progress（主 agent 收到了）。— 无 Token（上报本身不消耗；token_usage 随 payload 推送）
7
门禁① PRD 评审：人工确认需求边界与拆解合理性，通过则 hook 上报 gate_passed，推进 Dev；不通过则 gate_rejected，等待人工放行或退回 PM。— 无 Token（人工评审）
8
进入 Dev 阶段（并行分发）：Orchestrator 按 PM 产出的任务卡，生成 N 个 dev 子任务（t-...-0002 给 worker-B、t-...-0003 给 worker-C），逐个 produceTask，hook 上报 produced×N。🔤 消耗 Token（主 Agent 拆 N 个子任务）
9
多个 Worker 并行处理：worker-B/C 各自走步骤 2→6（拉取→query→trae-cli→ingest→回传）。每个 result 回来都产生 agent_complete + stage_progress 两条 hook。🔤 消耗 Token（N 个角色 Agent 并行调 LLM）
10
阶段收口：Orchestrator 对账该阶段所有 task_id 全部 success → 推进 Review；若有 failed → 触发容错（见下表）。🔤 消耗 Token（主 Agent 收口聚合）
…
后续 Review / QA / Deploy：同样按"分发→拉取→执行→回传→收口"推进，每步都 hook 上报，直到 trace_closed。🔤 消耗 Token（主 Agent 拆任务 + 角色 Agent 执行 + 收口）

④ 每一步出错的对应处理机制

出错点检测方式处理机制hook 上报事件
markitdown 清洗失败/不可用normalizeInput 返回 ok=false原样拷贝为 .md 继续喂 LLM，不中断normalized 带 converted=false, error=...，链路继续
任务消息校验不通过validateTaskMessage 抛 ValidationError拒绝投递，进死信 runtime/state/_dlq/，不触发执行validation_failed，附错误明细
Kafka 不可达（投递时）producer 超时/连接错误暂停分发 + 告警，待恢复后续传produce_failed，retry 由人触发或恢复后自动续
Worker 拉取后崩溃 / trae-cli 执行失败退出码非 0 → 结果 status=failed结果照常回传（带 error），Orchestrator 收到后：Dev 阶段 → 回退重做；其他阶段 → 升级人工agent_complete(status=failed) → stage_progress → retry_scheduled 或 escalated
Worker 离线 / result 长时间未回传Orchestrator 按 timeout_sec 检测未回执标记该 task_id 超时，重试 1 次；仍失败 → 回退 Dev 或升级人工timeout → retry_scheduled / escalated
Review 不通过结果 status=failed + 问题清单回退 Dev 阶段重做，重新 produceTaskstage_rolled_back(dev→dev) + retry_scheduled
重做超 3 轮仍未通过重做计数 >= 3停止重做，升级人工决策escalated，链路暂停等人
门禁未通过人工评审拒绝状态机暂停，等待人工放行或退回上一阶段gate_rejected
workerPoll 重入文件锁 worker.lock 占用直接退出，不并发执行（worker 侧本地日志，不上报 hook）
收口对账缺失 resultOrchestrator 对账 task_id 集合对缺失项按"超时未回传"处理result_missing → 走超时分支
Hook 后端不可达reportAgentComplete POST 失败/超时payload 落 runtime/hooks/_failed/，不中断主链路，可后续补发（本地落盘待补发；后端恢复后重发）
核心原则：每一步都通过 hook 上报 + 都有容错动作。trace_id 是唯一索引，所有事件都汇聚到 Hook 黑盒后端——任何一步出错都能从后端按 trace_id 定位到具体 stage / task_id / event，并触发对应处理（重试 / 回退 / 升级 / 死信 / 人工门禁）。本地不再保存链路状态文件，链路可观测性完全由 Hook 后端承担。
容错边界：重试最多 1 次、回退重做最多 3 轮，超出即升级人工（escalated），不会无限自动循环；Kafka/worker 故障期间链路暂停而非丢失，恢复后按 offset 续传；Hook 后端故障期间事件落本地 runtime/hooks/_failed/ 待补发，主链路不受影响。

⑤ Token 消耗点与推送（随 hook 上报）

系统只在"主 Agent 喂 LLM 拆任务/收口"和"角色 Agent 调 LLM 执行"时消耗 token；其余步骤（markitdown 清洗、Kafka I/O、知识库 query/ingest、hook 上报、校验/死信、人工门禁）均不消耗系统 token。所有 token 消耗量都随 agent_complete / stage_progress hook 推送到黑盒后端（字段 metrics.token_usage）。

角色职责执行（pm/dev/review/...）角色 Agent（worker）TRAE-B/C 账号trae-cli 输出 → outbox 结果 JSON 的 metricsagent_complete
阶段收口聚合主 Agent（Orchestrator）TRAE-A 账号Orchestrator 收口会话末尾读取stage_progress
token 推送链路：角色 Agent 执行 → trae-cli 输出 token_usage → 写入 outbox 结果 JSON 的 metrics.token_usage → buildAgentCompletePayload 读出 → 随 agent_complete hook POST 到 AGENT_HOOK_URL。主 Agent 的拆任务/收口 token 同理随 stage_progress 推送。黑盒后端可按 trace_id 聚合整条链路的总 token 消耗（主 Agent + 各角色 Agent 之和）。
不消耗系统 token 的步骤：markitdown（格式转换）、Kafka I/O、知识库 query/ingest（黑盒内部若用 embedding 属于黑盒自理，不计入系统）、hook 上报（HTTP POST）、校验/死信、人工门禁。这些步骤的 hook 上报 metrics 可省略或为 0。

Agent 完成 Hook（统一管理层 · 中间件①）

本中间件已收拢进 Agent 统一管理层（管道中间件①）。每个 agent 任务完成后经 emitAgentEvent 管道分发到此中间件，把本次详情 POST 到黑盒后端（AGENT_HOOK_URL）。与知识库 ingest 的区别：知识库存"精炼经验"，Hook 存"执行详情"（审计/监控/BI 用）。黑盒实现任意，系统侧只约定接口。

触发点（每个 agent 都有）

触发方时机eventagent_role含义
角色 Agent（worker 侧）triggerTrae 跑完之后、publishResults 之前agent_completepm / dev / review / qa / deploy一个角色 agent 完成了它的子任务

容错与配置

未配置 = no-op

AGENT_HOOK_URL 为空时 reportAgentComplete 直接返回，不报错、不落盘。系统默认能跑，Hook 是可选增强。

失败不中断

POST 失败/超时（10s）→ 把 payload 写入 runtime/hooks/_failed/<ts>-<task_id>.json，绝不抛错，主链路（produce/consume/publish）照常继续。

主 agent 去重

orchestratorCollect 周期扫描 results/ 目录，用 runtime/state/hooked.jsonl 记录已上报 task_id，避免重复 POST。

角色 agent 兜底

worker 侧 triggerTrae 异常或 outbox 结果文件缺失时，构造 status=failed 的 payload 照常上报，确保"失败"也能被黑盒感知。

黑盒边界：系统侧只约定 POST {AGENT_HOOK_URL} 与上述字段。后端如何存储、索引、告警、聚合，均不影响主链路，可独立演进或替换（审计系统 / 监控平台 / BI / 数据仓库 皆可）。

设计要点

省 token

Kafka 连接/轮询/回传全在 TS 脚本；agent 单次会话只执行一个任务；inbox 为空不启动 trae-cli；知识库查询/写入也由脚本完成，结果作为文本注入 prompt。

可解耦

Kafka 解耦编排者与 Worker；知识库黑盒解耦经验沉淀与主链路；trae-cli 非交互解耦 agent 与 IDE GUI。

可恢复

Kafka 持久化 + consumer offset + state/processed.jsonl 去重；worker 离线后上线续消费不丢任务。

可校验

所有消息 schema_version=1.0 + 必填/枚举校验；不合法进死信目录 runtime/state/_dlq/，不触发执行。

可控制

agent-control 主题下发 stop/pause/resume；workerPoll 下轮检测生效，不中断在执行任务。

可沉淀

知识库中间层把每次任务的总结转化为可召回资产，执行前查询注入，让 Worker 越做越聪明。
