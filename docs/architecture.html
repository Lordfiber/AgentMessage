多 TRAE 任务分发系统 · 整体设计

局域网内 3 台 Windows + TRAE：主 Agent（Orchestrator）接收需求并按团队路由，团队 Agent 分派（内部团队继续拆解 / 外部部门原样出文档），角色 Agent 定时触发执行，经 RabbitMQ 分发，知识库中间层沉淀与召回经验。

TypeScript / Node.js RabbitMQ（独立服务器部署） trae-cli 非交互触发 Windows 计划任务 知识库中间层（黑盒） 三层 Agent 体系（主 Agent + 团队 Agent + 角色 Agent） 可套娃扩展（Agent 节点树） markitdown 输入清洗（仅 Orchestrator） 端到端链路追踪 · trace_id 贯穿 + 每步容错 Agent 完成 Hook（黑盒后端） Agent 统一管理层（中间件管道）

组件说明

L1 · 主 Agent（Orchestrator / TRAE-A）

root · 需求路由层

唯一实例。接收原始需求 → markitdown 清洗 → 团队自动匹配（根据需求内容识别归属团队/部门，可涉及多个团队，不手动指定）→ produceTask 投给 L2 团队；生成 trace_id；总控研发状态机（PM→Dev→Review→QA→Deploy）；收口聚合 + 写知识库。3 道人工门禁；Review 不通过回退 Dev（≤3轮）。

L2 · 团队 Agent（分派层）

team dispatch

每个团队一个 agent（如云门禁团队、车行云团队），团队下有员工列表（如云门禁 sz_jsxt116/117、车行云 sz_jsxt118/119）。拆解型：收到需求后继续拆解，拆出团队任务后人工手动指派给团队内员工（可单人/多人并行，routing_key=员工 worker_id）→ 分发到 L3 角色 Agent；直传型（如云访客等外部部门）：不做需求分配，把需求原原本本转成一份需求文档交付。团队同样走中间件管道（hook/评审/总结自动生效）。

L3 · 角色 Agent（Worker / TRAE-B/C）

role executor

承载 5 角色之一（pm/dev/review/qa/deploy）。计划任务每 N 分钟唤醒：consumeTasks 拉任务 → 知识库 query → trae-cli run --file 执行角色职责 → 写结果 → 知识库 ingest → publishResults。

RabbitMQ 服务器

message bus

独立服务器部署（Linux 最稳，也可 Docker/WSL2/Windows，默认端口 5672）。三队列：agent-tasks（direct 交换机，routing_key=worker_id / team_id，精确路由到目标 agent）、agent-results、agent-control（stop/pause/resume）。队列 durable + 消息 persistent，消费者 ack 前不丢；agent 离线时消息堆积在队列，上线后继续消费。

知识库中间层（黑盒）

knowledge layer

不关心内部实现（向量库/全文/图谱皆可）。对外仅两个方向：写入总结的知识、查询获取本次需要的知识。供主 Agent、团队 Agent 与角色 Agent 在执行前后调用，沉淀经验、召回上下文。

触发器与计划任务

scheduler

workerPoll.ts（角色）与 teamPoll.ts（团队）文件锁防重入 + 检测 control stop 信号；triggerTrae.ts 可插拔（trae-cli 首选，IDE-UI 兜底）；registerTasks.ts 用 PowerShell 注册 Windows 计划任务。

markitdown · 输入清洗层

orchestrator-only

只在 Orchestrator/TRAE-A 启动时调用（仅它接收杂格式：doc/docx/pdf/txt/企业微信消息/手动输入）。命令：markitdown nio.pdf > nio.md。统一清洗为 Markdown 再喂给 LLM；markitdown 不可用/失败时原样回退，不中断流程。代码入口：src/orchestrator/normalizeInput.ts。

Broker 桥接层

zero-token I/O

所有 RabbitMQ 连接/轮询/回传都在 TS 脚本里，agent 不参与。produceTask / consumeTasks / publishResults / consumeResults + 契约校验 + 死信目录。

Agent 统一管理层（中间件管道）

cross-cutting concerns · 全部层级通用

所有 agent（主/团队/角色）生命周期事件都经 emitAgentEvent(ctx) 管道分发。横切关注点（hook/评审/总结/审计/token 统计）注册为中间件，加新关注点 = useAgentMiddleware 一行，零改动 agent 代码。入口 src/agent/。解决"每个 agent 后面重复加 hook/评审/总结"的冗余。

Agent 完成 Hook（中间件①）

audit / monitor / BI

统一管理层的第①个中间件：把各层 agent 完成详情 POST 到 AGENT_HOOK_URL 黑盒后端。未配置 → no-op；失败 → 落 runtime/hooks/_failed/，不中断主流程。底层传输 src/broker/hookReport.ts。

三层 Agent 体系与研发状态机

L1 · 主 Agent（需求路由层）

Orchestrator · 唯一实例 · TRAE-A

接收原始需求 → 清洗 → 识别需求归属团队/部门 → 路由给 L2。不拆具体任务（拆解交给 L2 团队 / L3 角色）。生成 trace_id，总控状态机与门禁。

L2 · 团队 Agent（分派层）

team · 一团队一 agent · 可多实例

拆解型（云门禁 / 车行云）：把需求继续拆成 L3 角色任务；直传型（云访客等外部部门）：不做需求分配，原原本本产出需求文档。团队 = 一个"小 Orchestrator"。

L3 · 角色 Agent（执行层）

5 角色 · 多实例并行 · Worker TRAE

pm（需求+拆解）/ dev（开发+修复）/ review / qa（占位）/ deploy（占位）。承接 L2 拆解后的任务，真正执行并回传结果。

三层职责对比

层Agent收什么做什么产出/发出消耗 Token
L1主 Agent（Orchestrator）原始需求（doc/pdf/消息）清洗 · 团队自动匹配（可多团队）· 生成 trace_id · 总控门禁→ 匹配到的 N 个团队任务（route_path 多分支）🔤 路由判断

拓展点 · 上下套娃（Agent 节点树）

三层只是当前实例，架构本身是任意深度的 Agent 节点树。每个节点是统一抽象：

AgentNode = {
  id: "team-cloud-door",        // 节点唯一 id（routing key / route_path 元素）
  name: "云门禁团队",
  mode: "dispatch" | "leaf",    // dispatch=继续下传（分派） | leaf=终结点（执行或文档化）
  leaf_behavior: "role" | "doc" // leaf 时的行为：角色执行 / 原样出文档（直传型）
  children: [AgentNode...]      // 子节点（任意深度，套娃的载体）
}

往下套娃

任何 dispatch 节点（团队）下可再挂子团队或角色：云门禁团队 → 门禁前端组 → dev。新增子节点 = 在 config/teams.yaml 加一段，不改代码。角色 mode=leaf / leaf_behavior=role，直传部门 mode=leaf / leaf_behavior=doc。

往上套娃

Orchestrator 之上可再挂"事业部 / 公司 Agent"：把 L1 也当 dispatch 节点，向上再长一层（事业部 → 主 Agent → 团队 → 角色）。L1/L2 的"路由 + 分发"逻辑完全一致，同一套代码递归复用。

路由机制

消息带 route_path: ["root", "team-cloud-door", "dev"] + target_agent_id。每个节点只消费 target_agent_id === 自己 的消息，然后决定 dispatch（更新 route_path 下传）或 leaf（执行/文档化）。任意深度都通用。

配置驱动

config/teams.yaml 定义整棵树：新增团队/层级/直传部门 = 改配置；中间件管道 / hook / trace / 死信 / 知识库对所有层级的节点自动生效，无需逐层实现。

Agent 统一管理层（中间件管道 · 横切关注点集中化）

问题：每加一个横切关注点（hook、评审、总结、审计、token 统计...）都要在每个 agent 后面重复一遍——冗余且易漏。

方案：所有 agent 的生命周期事件都经 emitAgentEvent(ctx) 统一管道分发；每个关注点注册为一个中间件，管道依次执行。加新关注点 = useAgentMiddleware 一行，零改动任何 agent 代码。

数据流

① 任务分发流（RabbitMQ 主链路）

0
markitdown 输入清洗（仅 Orchestrator）：杂格式原始输入 → npx tsx src/orchestrator/normalizeInput.ts <原始文件>（或 --text）→ 产出 runtime/input-clean/xxx.md，再把这份清洗后的 .md 喂给 LLM。失败/不可用自动原样回退，不中断。
1
L1 团队路由：基于清洗后的 .md，Orchestrator 识别需求归属的团队/部门，生成 route_path 第一跳 + target_agent_id（如 team-cloud-door / team-visitor），把需求封装为团队任务（含 directive + expected_output）→ npx tsx src/broker/produceTask.ts <task.json> 投递到 agent-tasks 队列，routing_key=team_id。
2
L2 团队分流：拆解型（云门禁/车行云）收到团队任务后继续拆解，追加 route_path 一跳、按角色封装子任务（routing_key=worker_id）再下传（PM 阶段由 PM Agent 拆任务，Dev 阶段并行分发多个 dev 任务）；直传型（云访客等外部部门）不做需求分配，把需求原原本本整理成需求文档直接交付，不经 L3。
3
角色 Agent 拉取：计划任务触发 workerPoll → consumeTasksForWorker 消费分给自己的消息 → 渲染 inbox/<task_id>.md + .json，按 task_id 去重。inbox 为空则直接退出（零开销）。
4
角色 Agent 执行：triggerTrae 调 trae-cli run --file <task_id>.md --output <result_file>，按 timeout_sec/max_steps 控上限，退出码映射 status。
5
结果回传：publishPendingResults 把 outbox 的结果发布到 agent-results 队列 → 团队/主 Agent 逐级 consumeResults 落 runtime/results/。
6
逐级收口：结果沿 route_path 反向逐级上收（团队 → 主 Agent），主 Agent 读 runtime/results 聚合推进状态机；失败可修正后重新投递。

② 知识库交互流（黑盒，两方向）

Q
查询获取（执行前）：Worker 拿到任务后、执行前，向知识库发查询请求（任务目标 + 关键词），获取本次内容需要的知识（历史经验、相关模式、上下文），作为 directive 之外的补充上下文注入 .md。编排者拆任务时也可查询以辅助拆解。
W
写入总结（执行后）：Worker 执行完成后、回传结果前，向知识库发写入请求，把本次的总结知识（做了什么、踩了什么坑、可复用的模式）沉淀进去。编排者收口后也可写入整体总结。
知识库中间层是黑盒：系统只约定"查询 / 写入"两个交互方向与请求/响应字段，内部存储、检索算法、向量化等一概不关心，可按需替换实现。

端到端链路追踪（trace_id 贯穿 + 每步容错）

一条需求从输入主 Agent 到被分发到的角色 Agent 处理，全程用链路唯一 ID（trace_id）串起来；每一步都通过 Agent 完成 Hook 把事件上报到黑盒后端（不再本地保存状态文件），任何一步出错都有对应的容错动作。这条链路是本系统的主干，比"数据流"更具体地展示了一个请求的完整生命周期与容错路径。

① 三级 ID 体系

ID谁生成粒度用途
trace_idOrchestrator（需求输入时）一条需求一条，贯穿 PM→Dev→Review→QA→Deploy 全程链路唯一标识，串联所有阶段/子任务/事件；这是用户给的"链路唯一 ID"
parent_task_idOrchestrator（每阶段切换时）一个阶段一个该阶段所有并行子任务的共同父 ID，便于阶段级聚合
task_idOrchestrator（分发每个子任务时）一个子任务一个RabbitMQ routing_key 之一、worker 去重、结果回传对账

关系：trace_id 1 → N parent_task_id（每阶段 1 个）→ N task_id（阶段内并行子任务）。route_path 记录节点树路径（如 ["root","team-cloud-door","dev"]），供任意深度套娃路由与逐级收口。所有 RabbitMQ 消息（task / result / control）都带 trace_id，worker 也会把 trace_id 写进产出文件头。

4 个黑盒系统：①markitdown 输入清洗、②知识库 query/ingest、③Hook 后端上报执行详情、④RabbitMQ 消息总线。3 类 Agent：L1 主 Agent（Orchestrator，唯一）+ L2 团队 Agent（拆解型 / 直传型）+ L3 角色 Agent（5 个，可多实例并行）。所有交互都带 trace_id + route_path，事件最终都汇聚到 Hook 黑盒后端，本地不再保存链路状态文件。

核心原则：每一步都通过 hook 上报 + 都有容错动作。trace_id 是唯一索引，所有事件都汇聚到 Hook 黑盒后端——任何一步出错都能从后端按 trace_id 定位到具体 stage / task_id / event，并触发对应处理（重试 / 回退 / 升级 / 死信 / 人工门禁）。本地不再保存链路状态文件，链路可观测性完全由 Hook 后端承担。
容错边界：重试最多 1 次、回退重做最多 3 轮，超出即升级人工（escalated），不会无限自动循环；RabbitMQ/worker 故障期间链路暂停而非丢失，恢复后从未确认消息继续消费（ack/requeue）；Hook 后端故障期间事件落本地 runtime/hooks/_failed/ 待补发，主链路不受影响。

⑥ Token 消耗点与推送（随 hook 上报）

系统只在"主 Agent 路由、团队 Agent 拆解/文档化、角色 Agent 调 LLM 执行、各层收口"时消耗 token；其余步骤（markitdown 清洗、RabbitMQ I/O、知识库 query/ingest、hook 上报、校验/死信、人工门禁）均不消耗系统 token。所有 token 消耗量都随 agent_complete / stage_progress hook 推送到黑盒后端（字段 metrics.token_usage）。

消耗点触发方消耗谁的 LLM tokentoken_usage 来源随哪个 hook 推送

容错与配置

未配置 = no-op

AGENT_HOOK_URL 为空时 reportAgentComplete 直接返回，不报错、不落盘。系统默认能跑，Hook 是可选增强。

失败不中断

POST 失败/超时（10s）→ 把 payload 写入 runtime/hooks/_failed/<ts>-<task_id>.json，绝不抛错，主链路（produce/consume/publish）照常继续。

主 agent 去重

orchestratorCollect 周期扫描 results/ 目录，用 runtime/state/hooked.jsonl 记录已上报 task_id，避免重复 POST。

角色 agent 兜底

worker 侧 triggerTrae 异常或 outbox 结果文件缺失时，构造 status=failed 的 payload 照常上报，确保"失败"也能被黑盒感知。

黑盒边界：系统侧只约定 POST {AGENT_HOOK_URL} 与上述字段。后端如何存储、索引、告警、聚合，均不影响主链路，可独立演进或替换（审计系统 / 监控平台 / BI / 数据仓库 皆可）。

设计要点

省 token

RabbitMQ 连接/轮询/回传全在 TS 脚本；agent 单次会话只执行一个任务；inbox 为空不启动 trae-cli；知识库查询/写入也由脚本完成，结果作为文本注入 prompt。

可解耦

RabbitMQ 解耦编排者与 Worker；知识库黑盒解耦经验沉淀与主链路；trae-cli 非交互解耦 agent 与 IDE GUI。

可恢复

RabbitMQ 队列 durable + 消息 persistent + 消费者 ack + state/processed.jsonl 去重；worker 离线时消息堆积在队列，上线后继续消费不丢任务。

可校验

所有消息 schema_version=1.0 + 必填/枚举校验；不合法进死信目录 runtime/state/_dlq/，不触发执行。

可控制

agent-control 队列下发 stop/pause/resume；workerPoll 下轮检测生效，不中断在执行任务。

可沉淀

知识库中间层把每次任务的总结转化为可召回资产，执行前查询注入，让 Worker 越做越聪明。
